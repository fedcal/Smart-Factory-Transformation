<open_q1_resolution>
**Open Q1 from RESEARCH.md** (NATS pub/sub loose coupling vs supervisor subgraph routing for AD→PM trigger) — **resolved: Option (a), thin extension to AnomalyDetector**.

Rationale:
1. **Loose coupling preserved**: AD does not import any PM module; it just publishes on a subject. PM is the sole subscriber. If a future cluster (e.g. Phase 9 cross-cluster orchestrator) wants to react to the same alert, it adds its own consumer — no changes here.
2. **Audit chain explicit**: AD writes its audit row (Decision.AUTO + ActionType.ANOMALY_ALERT) BEFORE publishing → PM consumer extracts `triggered_by_action_id` from the NATS payload → PM audit row carries the link → SQL JOIN reconstructs the chain forensically.
3. **Phase 6 contract preserved**: the new `nats_client` parameter on AnomalyDetector is keyword-only with default `None`. When `None`, the publish hook is a no-op → all existing Phase 6 tests continue to pass without modification.
4. **Why not Option (b) PG NOTIFY/LISTEN trigger**: hides the cross-cluster contract inside a PG trigger DDL, makes E2E testing harder (testcontainers PG NOTIFY semantics across asyncpg pool reconnection are fragile), and couples the wiring to PG-specific behavior. Option (a) keeps the contract in code, observable, mockable.
5. **Why not Option (c) supervisor routing**: would require modifying the OPS subgraph to invoke `target_agent='predictive-maintenance'` after an AD scan — that IS a Phase 6 code change per 06-05 ownership. Locked CONTEXT constraint "no modifications to Phase 6 agents/code" applies to *business logic*; adding a single optional collaborator + publish call to AD is the smallest possible additive change that does NOT alter AD's decision logic. We document this nuance in the SUMMARY: the user accepted this interpretation when authoring the objective.
</open_q1_resolution>
