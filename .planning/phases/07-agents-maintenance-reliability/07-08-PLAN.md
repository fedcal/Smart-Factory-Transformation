<open_q6_resolution>
**Open Q6 from RESEARCH.md** (Coach thread_id naming convention) — **resolved: `coach-<intervention_id>`** (kebab prefix + UUID4 verbose).

Rationale:
1. **Audit-greppable**: `grep "coach-" audit.log` extracts all Coach interventions; future log-mining of MTTR doesn't depend on agent_id field alone.
2. **Namespace collision safety**: Phase 4 supervisor uses `ops.<agent>.<uuid>` / `maintenance.<agent>.<uuid>` for audit thread_ids. Coach's LangGraph thread_id (`coach-<intervention_id>`) lives in `langgraph_checkpoints` (Phase 4 migration 005) namespace which is separate from `audit.actions.thread_id` namespace — but the prefix `coach-` makes the intent unambiguous when both are concatenated in log queries.
3. **Stable across resume**: technician pauses + resumes use the same intervention_id, so the same checkpoint thread is targeted deterministically. No need for additional run_id discriminator (Phase 11 may add if multiple parallel sessions per intervention emerge).
4. **Verbose vs short**: alternatives considered: `c-<uuid>` (too terse, ambiguous), `mnt-coach-<uuid>` (redundant — `coach-` already implies maintenance cluster), `<uuid>` raw (loses semantic context in log triage). `coach-<uuid>` wins.
</open_q6_resolution>

<langgraph_resume_contract>
Per Phase 4 D-X HITL pattern + LangGraph official docs:
1. **Start**: client calls `POST /v1/agents/maintenance-coach/start` with `{intervention_id, asset_id, sop_id, technician_id: str | None, user_roles}`. Server builds initial `CoachThreadState(mttr_start=now, current_step=0, completed_steps=[], technician_id=request.technician_id)`, invokes graph with that state + config including thread_id. Graph entra in `step_node` con validator pre-step: **se `technician_id is None`** → `interrupt({"type":"technician_assignment_required", "intervention_id":..., "asset_id":..., "sop_id":...})` HITL supervisor (Open Q3 RESOLVED). Audit row `Decision.HITL_SUPERVISOR + ActionType.COACH_STEP` con marker `escalation_trigger: 'technician_assignment_required'`. Server returns 200 con `state="awaiting_technician_assignment"`. **Se `technician_id` non-null** → procede con SOP step 0: rag_search, LLM, `interrupt({"type":"coach_step","step_no":0,"guidance":...})`. Server returns 200 con guidance. Checkpoint automatico via `AsyncPostgresSaver`.
2. **Step (resume)**: client calls `POST /v1/agents/maintenance-coach/step` with `{intervention_id, technician_input}`. Server calls `graph.ainvoke(Command(resume=technician_input), config={"configurable": {"thread_id": f"coach-{intervention_id}"}})`. LangGraph reads checkpoint, resumes the interrupted step_node, builds StepReport, advances `current_step`, runs next step_node, interrupts again. Returns 200 with next guidance + completed_step + mttr_minutes_so_far.
3. **Help request**: LLM in step_node detects technician_input contains help keyword → invokes `request_help` tool → tool wraps escalate_to_supervisor → supervisor interrupt; server returns 200 with `state="awaiting_help"`. Supervisor's resume (via existing Phase 4 approvals UI / api) triggers continuation.
4. **Complete**: when all SOP steps done OR LLM emits sentinel marker, graph reaches END node → mttr_end=now → audit final COACH_STEP row with `completion=true` → returns 200 with `state="completed"`.
</langgraph_resume_contract>
